# Разбор отчётов и решения по проекту

Дата: 14.10.2026. Основа:
- `01-market-research/report.md` — рынок (поисковый агент);
- `02-tech-analysis/reports/chatgpt-technical-report-2026-10-14.md` — техника (ChatGPT Deep Research).

## 1. Главное в пяти пунктах

1. **Схема технически реализуема, но главный риск не в коде.** Ни один поставщик публично не подтвердил, что собирает заказ
   под чужую этикетку Озона и сдаёт его в срок. Без этого всё остальное бессмысленно. Это первое, что нужно выяснить у Максима:
   как у него физически происходят упаковка, печать этикетки и сдача.
2. **Строим гибрид, а не всё сами.** Готовые сервисы закрывают учёт и рутину маркетплейса. Сами пишем только ядро, которого нет
   ни у кого: доступность и резерв у поставщика, маршрутизацию заказа и реестр сверки.
3. **Пилот — один поставщик, один физический маршрут, 100 карточек, из них 20 хитов.** Рост до 500–1 000 — когда выполнены
   критерии (раздел 3), а не по календарю.
4. **API Озона в 2026 году сильно поменялся.** Старые примеры кода из интернета опасны: FBS-списки v3, `finance/transaction`,
   `act/create` отключены, этикетки переходят на scanit с 05.10.2026, правила слотов меняются с 19.11.2026. Писать только по
   актуальной документации.
5. **LLM — для текста и разбора, не для денег.** Карточки, сопоставление артикулов, ответы покупателям, разбор возвратов и
   расхождений — да. Цены, остатки, закупки, налоги — только обычный проверяемый код.

## 2. Где отчёты сходятся и где расходятся

Объём на старте дадут хиты под трафик Максима, хвост из 80 проверит разнородность заказов. Каталог на 500 готовим заранее, чтобы включить его сразу после прохождения критериев |

Armtek — сервисы заказов есть, детали по договору | Кандидаты на пилот: **Rossko или Шате-М**, решающий фактор — согласие на сборку под этикетку Озона |
| Лимиты поставщиков | Не найдено | Rossko: 300 запросов/мин, 100 000/сутки; Шате-М: 2 000 за 15 мин, 120 000/сутки | Опрашивать 40 000 артикулов поштучно невозможно (11,5 млн запросов в сутки). Нужен массовый прайс + дельты + точечная проверка при заказе |

## 3. Критерии перехода между этапами

Берём из ChatGPT (раздел 7 его отчёта), с поправкой на хиты.

| Этап | Карточек | Перейти дальше, когда |
|---|---|---|
| 0. Проверка схемы | 0 | Есть договор с поставщиком; известно, кто печатает этикетку, сдаёт посылку и принимает возвраты; 10 сквозных тестовых сценариев пройдены |
| 1. Пилот | 100 (20 хитов + 80 хвоста) | ≥50 завершённых отправлений за ≥14 дней; ≥99% передано вовремя; ноль двойных закупок; каждая закупка связана с продажей |
| 2. Рост | 500–1 000 | ≥200 завершённых отправлений; отмены из-за отсутствия товара ≤0,5%; ≥99% вовремя; ≥99% суммы финансовых событий сопоставлено; закрыт первый месяц учёта |
| 3. Масштаб | 3 000–5 000 | Нагрузочный тест на двойной нагрузке пройден; есть второй независимый поставщик; вклад в прибыль положительный |
| 4. Широкий каталог | 10 000+ | 30 стабильных дней на предыдущем уровне |

Важно: на 50 отправлениях одна ошибка — это уже 2%. Пилот доказывает, что процесс работает. Что он устойчив, докажет только
большая выборка.

## 4. Где крутить LLM и автоматизацию

Это ответ на вопрос «где здесь крутить». Порядок — по эффекту на деньги и риск.

### Топ-5

| # | Точка | Что делаем | Почему первым |
|---|---|---|---|
| 1 | **Сверка «Озон ↔ поставщик ↔ банк»** | Код сопоставляет строки по надёжным ID и количествам. LLM только объясняет оставшиеся расхождения и извлекает поля из сканов УПД | Именно из-за этого ушёл бухгалтер Максима. Без этого масштаб невозможен, и это ваша зона ответственности как владельца ИП |
| 2 | **Сопоставление артикулов и брендов** | Код: точные совпадения и утверждённые справочники. LLM: кандидаты в синонимы брендов и дубли, которые утверждает человек | Ошибка здесь — продажа не той детали или двойная карточка. Ложное объединение дороже пропуска |
| 3 | **Генерация карточек** | LLM собирает название и описание только из утверждённых полей; валидатор кода сверяет с атрибутами Озона | Тысячи карточек вручную не сделать. Модель не должна добавлять ни одного факта, которого нет во входе |
| 4 | **Ответы на вопросы «подойдёт ли на мою машину»** | Агент читает карточку и проверенную применимость, готовит черновик. Если данных нет — просит VIN/уточнение или передаёт человеку | В автозапчастях это главный вопрос покупателя. Быстрый правильный ответ повышает конверсию, неправильный даёт возврат |
| 5 | **Разбор возвратов и отзывов** | LLM классифицирует причину по тексту и фото, готовит черновик ответа и чек-лист проверки | Возвраты нельзя вернуть оптовику автоматически. Нужно быстро понять, чья ошибка: наша, поставщика или покупателя |

### Где LLM не нужен и вреден

Остатки, цены, резервы, закупки, маршрутизация заказа, налоговые пороги. Здесь нужен обычный код с тестами: скорость,
предсказуемость, повторяемость. Ошибка модели здесь — прямые деньги.

### Правила для всех LLM-функций

1. Режимы по очереди: теневой (модель предлагает, никто не использует) → черновик с подтверждением человеком → автоматизация
   узких безопасных действий.
2. Текст из прайса, документа или сообщения покупателя — это данные, а не инструкции модели.
3. Структурированный вывод (JSON по схеме), проверка кодом, журнал: вход, версия модели, источники, кто утвердил.
4. Персональные данные покупателей (ФИО, адрес, телефон) в модель не передаём.
5. **Провайдер LLM для боевого сервера — открытый вопрос.** Сервер будет в России (152-ФЗ: персональные данные покупателей
   хранятся в РФ, к тому же так надёжнее доступ к API Озона). Claude API официально в России не предоставляется. Варианты:
   российский провайдер (YandexGPT, GigaChat) для вызовов с сервера, либо пакетная генерация контента здесь, в Claude Code,
   с загрузкой результата. В коде делаем адаптер, чтобы провайдера можно было сменить.

## 5. Архитектурные решения

| Решение | Выбор | Почему |
|---|---|---|
| Строим или покупаем | Гибрид: учёт в МойСклад или 1С (решает бухгалтер); ядро своё | Готового сквозного решения «Озон → оптовик → этикетка → сверка» ChatGPT не нашёл. **Сначала узнать, что использует Максим**: если у него уже работает ABCP или RDV, разумнее повторить его стек |
| Язык и фреймворк | Python 3.12, FastAPI | Много готовых библиотек для данных и LLM; проще читать вам |
| База | PostgreSQL | Деньги в копейках (целые), время в UTC, сырые ответы API хранить неизменными |
| Очереди | Таблица заданий в PostgreSQL + transactional outbox | Для 50 000 SKU отдельный RabbitMQ на старте не нужен. Очереди раздельные: заказы, обнуление остатков, команды поставщику, рост остатков, цены, каталог, финансы |
| Кабинет сборщика и оператора | Простые страницы на сервере (HTMX) | Поставщику нужен экран заданий: что собрать, этикетка, отметка «собрано/сдано» |
| Хостинг | VPS в России | 152-ФЗ, доступ к API Озона и поставщиков |
| Форма программы | Модульный монолит + фоновые обработчики | Модули с чёткими границами, разделять на сервисы — только по реальной нагрузке |

Формула публикуемого остатка (из отчёта ChatGPT):
`остаток на Озоне = min(лимит экспозиции, max(0, свободный остаток поставщика − наши неотражённые резервы − буфер))`.
На пилоте лимит — 1–2 штуки на товар; предложение с устаревшими данными закрывается автоматически.

## 6. Что нельзя делать

- Брать примеры кода для API Озона старше 2026 года без сверки с документацией.
- Суммировать остатки двух агрегаторов: они могут продавать один и тот же склад.
- Повторять закупку после сетевого таймаута, не проверив, создалась ли она.
- Выбирать самого дешёвого поставщика, если он не успевает к сроку отгрузки.
- Обещать применимость, если её нет в проверенном источнике.
- Считать прибыль Максима прогнозом для вашего магазина.
